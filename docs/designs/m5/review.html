Needs your approval

Start with the duplicate-attendance proposal, which changes how hosts handle a player who's already checked in. The numbered list below is every other proposal from the drafts. Orange ones change behaviour; the rest are copy or layout.

A player can never be checked in to the same session twice

Needs Ryan · D-A to D-D

What happens today

The database already allows only one attendance row per member per session. But if a host pressed Approve on a request for someone already attending, the approval would either fail with a technical error or "succeed" by moving that member's phone link to the new phone. The first draft also left Approve on the row ("Check with the player before approving"). Both are wrong.

Proposed rule

A check-in for someone already attending can't be approved. The host closes it as "already checked in", or rejects it if it isn't them. The player's phone learns the outcome only after a host decides.

  1. Own phone, already in. If the phone is already linked to that member and they're attending, the page answers at once with "You're already checked in" (P09). No request is created.
  2. Any other phone. The request is accepted and the phone shows "Waiting for the host to approve" (P06), the same as any request. This keeps the privacy rule: whoever holds the phone can't find out whether a named person is here.
  3. Tray row with no Approve. The row is marked "Already checked in to this session. They can't be added twice." The actions are "Close: already checked in" and "Reject" (H01).
  4. Outcome on the phone. "Close: already checked in" shows "You're already checked in" on the requesting phone (P09b). Reject shows the neutral "Please speak to the host" (P08). The phone is not linked to the member either way.
  5. Race between hosts. If the member is added after the row appeared (another host approved a request from a different phone, or added them in Who's playing), the row switches on the next 5-second update. An Approve already pressed is refused, and the row changes to "Approve stopped: already checked in" (H03).
  6. Enforced on the server. In M5 the approval function refuses an already-attending member (ALREADY_IN_SESSION) and never moves a phone link. The database's one-row-per-member rule stays as the final guarantee.
